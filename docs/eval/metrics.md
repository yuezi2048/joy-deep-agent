# 评测指标口径

> 这份文档定死「故障注入评测」要报的四个数字怎么算、单位是什么、边界怎么判。
> 报告格式见 `report-template.md`；场景库与执行见 issue #8。
>
> **口径先行**：数字只有能被复现才算数。这里写的每一项都对应代码里一个真实字段或事件
> （见文末「数据来源」表），没有「靠感觉」的项。

## 一、四个指标

### 1. 完成率（completionRate）

| 项 | 定义 |
| --- | --- |
| 分子 | 该场景下 `passed === true` 的运行次数 |
| 分母 | 该场景下的运行次数（同配置同场景重复 N 次，N 记为样本量） |
| 单位 | 比率 0~1；报告里同时给百分比，保留 2 位小数 |
| 判定 | **由场景预先声明的断言决定**，不看人；断言只允许读 `AgentRunResult`（`content` / `toolCalls` / `stopReason` / `messages`） |

判定示例（歧义处）：

- 任务是「把订单 42 改成已发货」，模型把**订单 43** 改了 → 断言失败 → 不算完成，哪怕 `stopReason === 'completed'`。
- 任务中途被墙钟上限截断（`stopReason === 'timeout'`）→ 一律算未完成：没有交付物就不算完成。
- 模型答对了但多调了一次工具 → 只要断言不关心调用次数，就算完成。

### 2. 恢复成功率（recoveryRate）

| 项 | 定义 |
| --- | --- |
| 分子 | 被**吸收**的注入故障数 |
| 分母 | 注入的故障数（一次运行可以注入多个） |
| 单位 | 比率 0~1 |
| 「吸收」 | 故障没有把任务带垮。显式恢复（同一类操作随后重新成功，`recoverFault`）直接算；没有显式恢复的故障，**只有任务断言通过**才算——循环「正常结束」不等于任务成功 |

与完成率的区别：**完成率看任务，恢复成功率看故障**。同一场景可以「恢复成功但未完成」——
例如注入 429 后被重试吸收，任务继续跑，但最终答案不符合断言。此时恢复成功率 100%、完成率 0%。

判定示例：

- 注入供应商 502 → 熔断打开 → 转移到备用供应商 → 备用返回结果 → **吸收**，恢复时间记从注入到备用成功。
- 注入供应商 502 → 所有供应商都挂 → 任务以异常结束 → **未吸收**（`recoveredAt` 为空），恢复时间不记入样本。
- 注入工具限流 → 重试三次仍失败 → 模型改用别的工具绕过去，任务跑完且断言通过 → **吸收**，恢复尝试次数记 3 次失败 + 1 次成功。
- 注入工具限流 → 模型放弃并回一句「我拿不到数据」→ 循环正常结束但断言不通过 → **不算吸收**：故障正是任务失败的原因。只看 `stopReason === 'completed'` 会把这种「带着失败观测正常收尾」误判成恢复。

### 3. 恢复时间（recoveryMs）

| 项 | 定义 |
| --- | --- |
| 计算 | `recoveredAt - injectedAt`，墙钟毫秒 |
| 聚合 | 每场景报 **P50** 与 **max**，并附样本数 |
| 单位 | 毫秒（整数） |
| 退避 | **按生产退避策略测，禁止为美化数字调小退避参数**；实际用的参数必须写进报告的 meta |

**必须与「恢复尝试次数」并列展示。** 恢复时间本质上是退避配置的函数（把
`initialDelayMs` 从 500ms 调成 50ms，耗时立刻好看十倍，但生产上并不成立）；
尝试次数与退避参数无关，是故障严重程度与系统策略的产物。两个数字并排放，
读者才能判断「快」是因为策略好，还是因为参数被调过。

判定示例：

- 注入时刻 1000ms，第一次重试在 1500ms 成功 → 恢复时间 500ms，恢复尝试次数 1。
- 注入时刻 0ms，退避 500ms → 1000ms → 2000ms，第三次成功 → 恢复时间 3500ms，尝试次数 3。

### 4. token 消耗（tokens）

| 项 | 定义 |
| --- | --- |
| 计算 | 单次运行取 `AgentRunResult.usage.totalTokens`；按场景聚合出**总量**与**均值** |
| 单位 | token |
| 含 | 加固自身的开销：自我核查那次调用、故障转移后的重发，都算进去 |
| 缺 | 供应商不返回 usage 时该次记为 `null`，均值只用有值的样本，并在报告里标注样本数 |

token 是**代价列**：加固通常会提高完成率，同时抬高 token；报告要同时给出，不能只报好的一面。

## 二、聚合算法（写死，避免各处口径不一）

- 比率：`分子 / 分母`，保留 2 位小数；分母为 0 时记 `null`（渲染成 `—`），**不写 0、也不写 100%**。
- P50：最近秩法——升序排序后取第 `ceil(0.5 × n)` 个（1 起数）；`n = 1` 时即该样本。不用插值，保证小样本可复现。
- max：样本最大值。
- Δ完成率：`加固 − 基线`，单位百分点（pp）。例：0.20 → 0.55 记 `+35pp`。
- Δ恢复成功率：同上，单位 pp。
- Δtoken：`(加固均值 − 基线均值) / 基线均值 × 100%`，保留整数百分比；基线均值为 0 时记 `null`。
- 任一侧样本量为 0 → 该侧的比率与耗时全部记 `null`，Δ 记 `null`，并在报告里标为**缺口**。

## 三、基线 / 加固的配置口径

「基线」= 裸循环：只有 ReAct 编排与工具本体，**所有加固层关掉**。
「加固」= 全套防护。两侧必须**同一场景、同一断言、同一模型、同样重复次数**，否则差值没有意义。

| 防护项 | 基线（裸循环） | 加固（全套） |
| --- | --- | --- |
| 工具中间件链 | 不装（无去重/预算/熔断/重试/超时） | 去重 → 预算 → 熔断 → 重试 → 超时 |
| 供应商故障转移 | 单供应商，失败即失败 | 多供应商 + 每供应商独立熔断 + 按优先级转移 |
| 重试策略 | 无 | `initialDelayMs=500`、`backoffFactor=2`、`maxDelayMs=15000`、`maxRetries=3`（**生产值**） |
| 检查点 / 续跑 | 关 | 开 |
| 无进展指纹 | `noProgressLimit=0`（关） | `noProgressLimit=3` |
| 横跳检测 | `maxCyclePeriod=0`（关） | 周期 2~3、重复 2 次 |
| 墙钟上限 | `maxDurationMs=0`（不限） | `maxDurationMs=300000` |
| 幻觉防护 | 关 | 来源约束 + 自我核查（最多 2 轮修正） |
| 工具前置依赖 | 不声明 `requires` | 按场景声明 |
| 启动预检 | 跳过 | 开 |
| `maxSteps` | 与加固一致（同一场景同一上限） | 8（或场景声明值） |
| 模型与温度 | 与加固一致 | 与基线一致 |

`maxSteps` 两侧保持一致：它属于**任务预算**，不属于加固项。用不同的步数上限去比完成率，
等于把预算差当成防护收益。

## 四、恢复率不是每个场景都有：仪器覆盖

恢复成功率与恢复时间都要求「注入时刻」和「恢复时刻」可观测。可观测性来自代码里的探针：

| 故障类别 | 注入探针 | 恢复探针 | 是否有恢复指标 |
| --- | --- | --- | --- |
| 失败调用 | 重试中间件 `onRetry`、`AgentEvent.tool_result`（`isError`） | 同一类操作的下一次成功结果 | 有 |
| 供应商故障 | `FailoverChatModel.onEvent`（`failed`） | `FailoverChatModel.onEvent`（`succeeded`，带尝试次数） | 有 |
| 用户中断 | 场景在 abort 处调 `injectFault` | 续跑成功后调 `recoverFault` | 有 |
| 终端环境异常 | 预检前调 `injectFault` | 预检判定不可写后调 `recoverFault` | 有 |
| 幻觉 / 工具误用 / 死循环 / 上下文溢出 | 无（没有「某个时刻坏了」的语义） | 无 | **无，报告里记 `—`** |

后四类的防护是**拦截式**的（不让错误发生），不是**恢复式**的（发生后再修好），所以没有恢复时间可言。
报告里记 `—` 是如实标注「测不了」，不是失败，也不会被静默省略。

## 五、数据来源（口径自查）

| 指标需要的量 | 代码里的来源 |
| --- | --- |
| 是否完成 | 场景断言的返回值 `passed` |
| 停止原因 | `AgentRunResult.stopReason` |
| 故障注入时刻 | 场景注入时调用 `RunRecorder.injectFault()`，或由事件适配器自动记账 |
| 故障恢复时刻 | `RunRecorder.recoverFault()`；适配器接 `FailoverChatModel` 的 `onEvent`、重试中间件的 `onRetry`、`AgentEvent.tool_result` |
| 恢复尝试次数 | 重试回调的 `attempt` 计数 + 成功那次 |
| token | `AgentRunResult.usage.totalTokens` |

**不设指标的东西**：模型「聪不聪明」、答案「好不好读」这类没有客观判定的项一律不测——
测不出来的数字写进报告只会污染判断。

## 六、缺口

报告必须留出「本类尚未加固」的位置：

- 场景声明的 `gaps`（例如「本类未加固：检查点未开启」）原样列进报告；
- 加固侧样本量为 0 的场景，自动标为缺口，不静默省略。

缺口不是失败，是**待办**：写明缺什么，比给一个好看的平均值有用。
